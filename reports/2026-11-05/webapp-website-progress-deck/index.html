What the findings look likeFour recurring patterns, in plain terms

The same few problems, repeated across the system.

A

Buttons that do nothing yet

The element from the design exists but is not connected to the backend. Clicking does nothing or silently fails.

B

Wrong or broken data on screen

A wrong value, a dead file link, or a missing validation rule. Usually the screen and the API disagree about what a field means.

C

Flows that stop halfway

A multi-step journey (invite, accept, assign) fails at one step, so the flow cannot complete.

D

Access wider than intended

An account sees or changes data it should not: one clinic reaching another's records, or any admin changing restricted settings.

Pattern D is non-negotiable before any real user: most of the 78 must-fix findings sit here. Most share one fix: enforce "who owns this record" in the backend, everywhere.
A and B get much faster to fix once screens and APIs agree each field (slide 9)Few causes, many symptoms
Our analysis · why this happenedNot effort: shared understanding

The team built fast, but without one shared picture.

1

No single agreed data contract

Backend and the two frontends were built separately, each choosing its own field names and shapes, so screens and APIs drift apart. Most "wrong data" and "dead button" findings start here.

2

Workflow knowledge lives in documents, not in heads

The requirements are detailed but long. Developers worked task by task and tested the happy path. Nobody held the whole picture of how data moves between screens and roles.

3

"Done" meant "task closed"

Tasks closed when code was written, not when the scenario passed. Bugs surfaced only when someone else re-ran the flow.

4

Older backend core carrying new logic

The backend was inherited and extended heavily. Old and new parts overlap, ownership checks are uneven, activity records incomplete. Structural problems need structural fixes.

All four apply to every module, not only the tested onesFix the reasons system-wide and the symptoms collapse
What we are changingStarted this week · whole system

From "test, report, fix, repeat" to agree once, fix by cause, verify by scenario.

1 · One data contract per screenA field-by-field agreement between each screen and its API: what each field is, where it comes from, who may read or write it.
2 · One map of the whole systemAll workflows and data flows on one visual map, so everyone sees how a change in one place affects the rest.
3 · Fix by root cause, not by ticketAbout twelve fix groups (ownership checks, settings permissions, audit trail, duplicate routes, currency). Each is fixed once across the whole codebase, tested and untested modules alike, including APIs the mobile app uses.
4 · Developers run the scenarios themselvesScripted scenarios, including edge cases, written from the requirements up front. A task is done only when they pass.
5 · Senior backend reviewAn experienced external engineer reviews the backend core and guides the structural fixes to access control and older routes.
6 · Launch in phases, not all at oncePhase 1 (onboarding, inquiry, quote) goes first with a small clinic group. Later phases follow when their checks pass. Priorities are the client's call.
