## How to Fill In This File

1. One tester runs a batch at a time; do not share a batch file with another tester during a run. Before starting, add your entry to **Tester** (`Name (YYYY-MM-DD)`) and **Build tested** (`<build> (YYYY-MM-DD)`) in Batch Control. Entries accumulate, separated by `; `, for example `Linh (2026-10-20); Minh (2026-11-02)`. Replace the `{...}` placeholder on the first run; never delete earlier entries.
2. Run cases in table order unless a case says otherwise.
3. In each case row, fill only these columns:
   - **Actual result / data**: what you observed and the exact values you entered, for example "Saved; status shows Draft; total 2,450 USD".
   - **Result**: `Not tested`, `Pass`, `Fail`, or `Blocked` (give the reason in Notes). `Retired` is set by the plan owner only.
   - **Notes**: usability observations (what you did, what happened, why it was confusing or slow), even when the case passes, plus any questions.
   - **Evidence**: links to your screenshots or recordings, separated by `, `. Upload each file to any file-sharing service you choose, with a link the team can open, named `<case base ID>-<YYYYMMDD>-<n>.<ext>` (run date, then a counter), for example `PR02-FR004-03-20261019-1.png`, so a retest never overwrites earlier files. Record only the links; do not send files with the batch.
   - **Bug status**: set `Found` when you see a bug; otherwise leave `—`.
   - **Last tested**: the date you ran the case, `YYYY-MM-DD`.
4. The team fills **Bug ID** and moves Bug status to `Logged`, `Fixed - retest`, `Closed`, or `Reopened`. When you retest a `Fixed - retest` case, update only the result columns.
5. Do not edit IDs (keep the ` r1` suffix), titles, preconditions, test data, steps, or expected results, and do not use the vertical-bar character inside cells. Put questions or proposed changes in **Notes**.
6. Keep each case row on one physical line. For a line break inside a cell, type `<br>`; pressing Enter splits the row and the file is rejected.

## Flow Overview

Phase 2 lets patients pay for and receive treatment, so the admin team needs a minimum, trustworthy set of billing controls before paid bookings run at scale. This batch covers only those controls on the admin dashboard: finding and reading patient invoices (FR-017 › Screen 4 Patient Billing - Invoice Management and Screen 4a Patient Invoice Detail), refunding a paid booking under the graduated cancellation policy (FR-017 › Screen 4b Refund Confirmation Modal, Rule 7, User Story 6), manually overriding a payment status when a payment webhook fails (Screen 4 › Manual Payment Status Override), sending a payment reminder, downloading the invoice PDF, and confirming that each money-moving action is re-authenticated and written to the audit log (Screen 7 › Tab 2 Audit Log, Audit Rule). It also checks the Phase 2 safety case where a payment arrives after a provider suspension or deactivation cancelled the booking (Workflow B3, Rules 13 and 14).

The exit gate for Phase 2 says billing must use the current invoice routes. Every case therefore checks that the invoice values shown come from the live booking (accepted price after promotion, locked currency, real payment history) and never from sample or fallback data.

Actors: Super Admin `{A1}` (Billing Admin rights) and Billing Viewer admin `{A3}` for the read-only check. Patients and providers appear only as existing setup data. Provider payouts, payout statements, affiliate billing, discount ROI, the revenue dashboard, dispute resolution, and currency alerts are Phase 3 and are not tested here.

Screen paths used in this batch (admin dashboard URL in plan.md section 3):

- Patient Billing (Screen 4): main navigation "Billing & Finance" > "Patient Billing".
- Patient Invoice Detail (Screen 4a): Patient Billing > "View Details" on an invoice row.
- Refund Confirmation Modal (Screen 4b): "Process Refund" on an invoice row or on Screen 4a.
- Audit Log: main navigation "Billing & Finance" > "Transaction Search & Audit Log" > "Audit Log" tab.
