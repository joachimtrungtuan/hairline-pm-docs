## How to Fill In This File

1. One tester runs a batch at a time; do not share a batch file with another tester during a run. Before starting, add your entry to **Tester** (`Name (YYYY-MM-DD)`) and **Build tested** (`<build> (YYYY-MM-DD)`) in Batch Control. Entries accumulate, separated by `; `, for example `Linh (2026-10-20); Minh (2026-11-02)`. Replace the `{...}` placeholder on the first run; never delete earlier entries.
2. Run cases in table order unless a case says otherwise.
3. In each case row, fill only these columns:
   - **Actual result / data**: what you observed and the exact values you entered, for example "Saved; status shows Draft; total 2,450 GBP".
   - **Result**: `Not tested`, `Pass`, `Fail`, or `Blocked` (give the reason in Notes). `Retired` is set by the plan owner only.
   - **Notes**: usability observations (what you did, what happened, why it was confusing or slow), even when the case passes, plus any questions.
   - **Evidence**: links to your screenshots or recordings, separated by `, `. Upload each file to the evidence folder the team shares with you, named `<case base ID>-<YYYYMMDD>-<n>.<ext>` (run date, then a counter), for example `PR02-FR004-03-20261019-1.png`, so a retest never overwrites earlier files. Record only the links; do not send files with the batch.
   - **Bug status**: set `Found` when you see a bug; otherwise leave `—`.
   - **Last tested**: the date you ran the case, `YYYY-MM-DD`.
4. The team fills **Bug ID** and moves Bug status to `Logged`, `Fixed - retest`, `Closed`, or `Reopened`. When you retest a `Fixed - retest` case, update only the result columns.
5. Do not edit IDs (keep the ` r1` suffix), titles, preconditions, test data, steps, or expected results, and do not use the vertical-bar character inside cells. Put questions or proposed changes in **Notes**.
6. Keep each case row on one physical line. For a line break inside a cell, type `<br>`; pressing Enter splits the row and the file is rejected.

## Flow Overview

This batch checks how a clinic runs a paid treatment from the procedure day to the end of treatment (FR-010 › Main Flow, steps 1–14).

1. The patient has paid in full and the booking is Confirmed. On the procedure day a clinician opens the booking from the Confirmed list in Patient Management and clicks **Check In**. Check In works only when the procedure date is today or earlier, nothing is left to pay, and the user is an Owner, Manager or Clinical Staff (Rules 3 and 4, Payment Rule 2).
2. Check In moves the case to In Progress. The clinician adds a Beginning Note and photos, then updates each relative treatment day (Day 1, Day 2, …) in the Day Edit Modal.
3. When every day has a final status (Finished, Need caution/attention or Cancelled/Deferred), **End Treatment** opens the End of Treatment Modal. Saving it completes the documentation and hands the case to aftercare (FR-011). Batch B03 continues from there.

The batch also covers:

- Changing the treatment details before Check In (Alternative Flow A2).
- An early arrival (Alternative Flow A1).
- Closing a case that cannot go ahead (Alternative Flows B2 and B4).
- The 12-hour and 24-hour documentation reminders and the admin "Overdue Documentation" flag (Rule 6; Edge Cases, provider forgets to complete documentation).

It also checks the treatment invariants in the Phase 2 exit gate:

- Check In gates for date, payment and role.
- One In Progress treatment per patient is not tested here: FR-003 allows one active inquiry per patient, so the two-booking setup cannot be built. PR03-FR010-05 is retired and the conflict is on the PO list.
- The plan, clinicians and graft estimate lock at Check In.
- Only five day statuses exist; "Pause" is not one of them.
- End Treatment opens only when every day is final, and the completion fields are required.
- Documentation cannot be edited after completion.
- Only the clinic that treats the patient can see the case.

Admin oversight of the same cases is in B02.

**PRD gaps that affect this batch:**

- Screen 4 shows **Cancel / Close Case** only while the case is In Progress. Alternative Flows B1 and B2, however, use it before Check In. PR03-FR010-19 follows Flow B2; if the button is missing on the Confirmed booking, mark Fail and the team triages it against Screen 4.
- B2 names the reason "Medical postponement", but the B4 reason list says "Medical". PR03-FR010-19 expects the B4 list.
- The PRD gives no exact message for the outstanding-balance block, or the early-arrival prompt, and does not say how far before the appointment time counts as an early arrival.
- The PRD does not name the admin notification list or a size limit for the Head Scan Photo Sets (V1).
- The PRD does not give the reminder wording or say where the admin dashboard shows the "Overdue Documentation" flag (Edge Cases). PR03-FR010-20 and PR03-FR010-21 record what is shown.
- Rule 7 (one In Progress treatment per patient) cannot be reached while FR-003 allows only one active inquiry per patient. PR03-FR010-05 is retired.

Record the text you see.
